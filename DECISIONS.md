# Решения по проекту

## Источник и парсинг
- Источник: docx с текстом ТК РФ (редакция с изменениями до закона от 06.04.2024 N 70-ФЗ). Выбран docx, потому что абзацы в нем целые и не нужна склейка рваных строк, как в txt.
- Сырой текст не хранится в git (папка data/ в .gitignore).
- Вырезаем: пометки «(в ред. ...)», редакторские справки «Действие ... распространяется на правоотношения...», подпись под кодексом, утратившие силу статьи (85, 175, 351.2, 360).
- Оставляем: ссылки на другие законы внутри текста статей и статью 422 (перечень утративших силу законов).
- Номера статей хранятся строками (бывают 5.1 и 348.11-1).
- Результат: 524 статьи, 0 дублей номеров.

## Чанкинг
- В каждый чанк добавляется заголовок статьи, чтобы фрагмент не терял контекст.
- Замеры: статья целиком даёт 131 из 524 чанков длиннее 2000 символов (максимум 11920), хвост такой статьи эмбеддинг-модель может обрезать. Поэтому «статья целиком» остаётся только как baseline.
- Кандидаты: до 1500 символов (840 чанков) и до 800 символов (1328 чанков). Выбор делаем по Recall@k на dev-вопросах, не раньше.
## Gold set
- Вопросы q01-q50 написаны мной самостоятельно.
- Gold set разделён на dev (~60%) и test (~40%) скриптом со стратификацией по типу вопроса, seed 42. Все настройки подбираются только на dev, test смотрим один раз в конце.
## Baseline (BM25, dev, 24 вопроса с ответом)
- Стеммер Snowball для русского. R@5 около 0.8, MRR около 0.6, размер чанка на BM25 не влияет в пределах шума (при 24 вопросах 1 вопрос = ~4 п.п.).
- R@10 = 0.81 у всех стратегий: около пятой части вопросов BM25 не находит вообще (гипотеза: разные слова у вопроса и статьи, проверяем разбором ошибок).
## Разбор ошибок BM25 (dev, чанк 1500)
- 7 из 24 вопросов с ответом не попали в топ-3. 5 из 7: разрыв словаря (бытовые слова в вопросе, юридические в статье). 1: заголовок статьи «Общие положения» без смысла (ст. 273). 1: соседние статьи про ту же тему (ст. 246), вопрос спорный, метку не менял.
- Метки gold set после просмотра ошибок не менялись.
- Гипотезы: (1) название главы в тексте чанка, (2) векторный поиск против разрыва словаря, (3) гибрид BM25 + вектор.
## Результаты поиска (dev, 24 вопроса, названия глав в тексте чанка)
- dense (e5-small) лучше BM25 на всех стратегиях чанкинга: MRR ~0.80 против 0.61-0.67.
- Размер чанка метриками не различается (разница 1-2 вопроса). Выбрано до 1500 символов по причинам, а не по цифрам: «статья целиком» обрезается моделью (131 статья длиннее 2000 симв.), 800 символов даёт мало контекста для генерации.
## Dense против BM25 (dev, 24 вопроса, чанк 1500, bootstrap 10000)
- MRR: +0.13, 95% [-0.01; +0.28]. Recall@5: +0.06, 95% [-0.10; +0.23]. По вопросам: dense лучше 8, хуже 3, равно 13.
- Вывод: тенденция в пользу dense, но интервалы включают ноль, преимущество на 24 вопросах не доказано.
- Решение: dense основной поиск (тенденция + механизм: разрыв словаря бытовых и юридических слов), BM25 остаётся baseline. Гибрид проверим только если останется время.
## Генерация, первый прогон на dev (24 вопроса с ответом, 5 без ответа, top-5 фрагментов, Qwen2.5-7B-Instruct)
- Все нужные статьи в контексте: 21 из 24. Ложных отказов: 1 из 24 (q33, нужной статьи в контексте не было). Нужные статьи процитированы в 20 из 23 ответов. Ссылок на статьи вне контекста: 0. Правильных отказов: 5 из 5 (вопросы без ответа лёгкие, далёкие от трудового права).
- Ошибки: 3 из-за поиска (q17 неполный ответ, q33 отказ, q40 уверенный ответ по чужой ст. 292 вместо 71), 1 из-за генерации (q28: нужная ст. 246 была в контексте, модель сослалась на 235 и 248).
- Вывод: основная потеря на этапе поиска. Самый опасный тип ошибки: неправильный контекст ведет к уверенному неверному ответу (q40).
- Ограничение: «статья процитирована» не равно «ответ верен», содержательную проверку делаем вручную.

## Сервис
- FastAPI: POST /ask и GET /health. Индекс строится при старте. create_app(index) принимает заглушку, поэтому тесты не загружают torch и модель.
- Локально сервис работает без языковой модели: ответ это самый релевантный фрагмент кодекса со ссылкой [ст. N] и список источников, в поле note это сказано явно.
- Генерация (Qwen на Kaggle) в сервис не подключена: нет GPU и API-ключа. Подключение сводится к замене функции extractive_answer. Метрики ответов в README относятся к пакетному режиму, а не к этому сервису.
## Пайплайн обновления индекса
- Логика в src/rag_labor_code/pipeline.py (запускается и тестируется без Airflow), DAG в dags/labor_code_dag.py это тонкая обёртка (Airflow 3, airflow.sdk, TaskFlow). Airflow не работает на Windows, DAG проверяем в CI на Linux.
- Шаги: хеш источника -> docx в текст, разбор и проверка (число статей 400-700, первая «1», нет дублей и пустых) -> индекс и метрики на dev -> порог MRR >= 0.70 -> публикация версии data/index/<хеш>/ и указателя CURRENT.txt. Состояние (хеш) обновляется только после успешной публикации, поэтому при провале проверки следующий запуск повторит всё.
- Порог 0.70 выбран ниже наблюдаемого 0.80 с запасом на шум (24 вопроса): он ловит поломку (например, плохой парсинг), а не мелкие ухудшения. Метрики на dev здесь служат мониторингом, а не доказательством качества.
- Проверено локально: первый запуск публикует версию f959e47f (MRR 0.799, Recall@5 0.896 на dev, совпадает с ручным экспериментом), повторный запуск пропускает работу по хешу.
- Не проверено: сам DAG (ждёт CI), ветка «порог не пройден». Ограничение: сервис пока строит индекс заново при старте и не читает опубликованную версию из data/index (загрузка из CURRENT.txt это следующий шаг).
- Сервис при старте читает опубликованную версию индекса через data/index/CURRENT.txt (быстрый старт); если версии нет, строит индекс сам. Тесты проверяют публикацию версии и блокировку по порогу MRR.
