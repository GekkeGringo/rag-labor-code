Вопросы по Трудовому кодексу РФ (RAG)

Учебный проект: система отвечает на вопросы по Трудовому кодексу РФ и ссылается на конкретные статьи. Это не юридическая консультация. Главная цель проекта не сам сервис, а честная оценка: что даёт поиск, что даёт языковая модель и где система ошибается.

Кодекс взят в редакции с изменениями до Федерального закона от 06.04.2024 N 70-ФЗ, поэтому часть норм может быть устаревшей. Источник текста: [https://courson.ru/knowledge/documents/labor-code-of-the-russian-federation]. Сам текст в репозитории не хранится.

Что сделано
Разбор docx кодекса на статьи (524 статьи), очистка от редакторских пометок, подписи и утративших силу статей.
Нарезка на фрагменты до 1500 символов с заголовком статьи и названием главы.
Векторный поиск (intfloat/multilingual-e5-small, работает на CPU) и baseline на BM25.
Генерация ответа с цитированием статей и правилом отказа. Модель Qwen2.5-7B-Instruct запускалась пакетно на Kaggle (локально нет GPU и API-ключа).
Оценочный набор из 56 вопросов, разделённый на dev и test, оценка поиска и ответов с доверительными интервалами.
Сервис FastAPI (/ask, /health), пайплайн обновления индекса, DAG для Airflow, CI на GitHub Actions.
Схема
docx -> текст -> разбор на статьи -> фрагменты -> индекс (e5-small)
                                                     |
вопрос -> топ-5 фрагментов -> [Kaggle: Qwen2.5-7B] -> ответ со ссылками [ст. N] или отказ

Пайплайн обновления (pipeline.py, DAG dags/labor_code_dag.py): хеш источника -> разбор и проверка -> индекс и метрики на dev -> порог MRR >= 0.70 -> публикация версии data/index/<хеш>/. Состояние обновляется только после успешной публикации. Сервис читает опубликованную версию по CURRENT.txt.

Данные и оценка

56 вопросов в eval/gold.csv: 39 одной статьи, 2 на две статьи, 15 без ответа в кодексе (из них 6 «рядом с темой»: МРОТ, взносы, пенсия, пособие, штраф, хранение дел).

Все вопросы придуманы автором
Разбиение на dev (29) и test (27) сделано скриптом со стратификацией по типу вопроса (seed 42). Все настройки подбирались только на dev. Конфигурация заморожена git-тегом pre-test-freeze, test открыт один раз.
Оценка ответов по смыслу (ok / partial / wrong): автор. 
Оценки на test ставил автор.
Результаты
Поиск (вопросы с ответом)
	dev (24) BM25	dev (24) dense	test (17) BM25	test (17) dense
Recall@5	0.83	0.90	0.59	0.94
MRR	0.67	0.80	0.49	0.91

Разница MRR (dense минус BM25): на dev +0.13, 95% интервал bootstrap [-0.01; +0.28]; на test +0.42, интервал [+0.25; +0.61], dense лучше на 11 вопросах, хуже на 0. На dev преимущество не было доказано, на отложенном test подтвердилось. Абсолютный уровень оценён грубо (17 вопросов).

Ответы на test (17 вопросов с ответом, оценка по смыслу)
Режим	полностью верно	верно или частично	неверно
closed (модель без поиска)	1 (6%, [1; 27]%)	5	12
rag (наша система)	12 (71%, [47; 87]%)	16	1
oracle (фрагменты нужных статей)	14 (82%, [59; 94]%)	17	0

Интервалы Уилсона 95%. На 10 вопросах без ответа rag не выдумал норму ни разу (10 из 10), closed выдумал нормы и ссылки в двух (страховые взносы, пособие по безработице).

Выводы:

Поиск даёт большой выигрыш: интервалы closed и rag не пересекаются.
Rag и oracle статистически не различимы (2 вопроса). Единственная ошибка поиска на test: q22 (нужная статья не попала в топ-5). В q08 нужная статья стояла пятой, модель ответила по соседней, и сам вопрос двусмысленный.
Слабое место теперь генератор: даже с идеальным контекстом 14 из 17, модель теряет условия и оговорки (q21, q25, q39).
Эксперименты на dev
Размер фрагмента (800 / 1500 / статья целиком) метриками не различается; выбрано 1500 по причинам: статья целиком обрезается моделью эмбеддингов, 800 даёт мало контекста.
Название главы в тексте фрагмента: небольшой плюс, в пределах шума, принято.
Промпт v2 (разбивать вопрос на части, сохранять условия) против v1: по заранее заданному критерию (отказы 5 из 5 и не менее 14 полностью верных) v2 отклонён: 12 против 14. Остаётся v1.
Ограничения
Малый оценочный набор (56 вопросов), интервалы широкие; различия в 1-2 вопроса считать выводом нельзя.
Один судья, часть вопросов писал он же; на dev оценки ставил он же. Корректность по смыслу проверялась без второго эксперта.
Дефект разметки: в q08 указана одна статья, хотя подходит и вторая. Метку после просмотра результатов не менял.
Локальный сервис отвечает без языковой модели: показывает наиболее релевантный фрагмент и список источников. Метрики ответов относятся к пакетному режиму на Kaggle, а не к сервису.
Отказ распознаётся по тексту ответа («нет ссылок и есть слово "нет"»), это хрупко; надёжнее структурный ответ с отдельным полем.
В топ-5 часто повторяются фрагменты одной статьи, то есть реальное число разных статей в контексте меньше пяти.
В ответах режима без поиска модель в двух случаях вставила китайский текст.
CI проверяет тесты и то, что DAG собирается в Airflow 3.0.6, но не выполняет задачи DAG (в репозитории нет данных кодекса).
MLflow не использовался: экспериментов мало, все они записаны в DECISIONS.md.
Идеи для следующей итерации (на test не проверялись)

Дедупликация фрагментов по статьям, больше фрагментов, пересортировка, гибрид BM25 и dense, более сильная модель, структурный ответ с полем отказа, второй эксперт для оценки ответов.

Как запустить
uv sync
# положить docx кодекса в data/raw/tk_rf.docx (источник указан выше)
uv run python -m rag_labor_code.pipeline        # разбор, индекс, метрики на dev, публикация версии
uv run uvicorn rag_labor_code.service:create_app --factory
uv run pytest

Первый запуск скачивает модель эмбеддингов с Hugging Face. Генерация ответов: notebooks/generate_kaggle.py и notebooks/generate_kaggle_test.py (ячейки для ноутбука Kaggle с GPU).

Структура
src/rag_labor_code/: разбор (parser.py), фрагменты (chunker.py), индексы (dense.py, retrieval.py), пайплайн (pipeline.py), сервис (service.py), скрипты оценки (evaluate_*.py).
dags/: DAG для Airflow.
eval/: оценочный набор, оценки ответов, результаты.
notebooks/: код генерации для Kaggle.
tests/: тесты.
DECISIONS.md: журнал решений с причинами и цифрами.
